# Authentication

Accounts (storage layout, selection, migration of the 0.3.0 token, the Drive dependency): `accounts.md`. This file covers the OAuth client, scopes, flows and refresh tokens.

## Files

| File | Location | Owner | Mode |
|---|---|---|---|
| `client_secret.json` | `$XDG_CONFIG_HOME/gdcli/` (default `~/.config/gdcli/`) | user (downloaded from Google Cloud, edited by the user) | 0600, directory 0700 when created by gdcli |
| `accounts/<email>.json` | `$XDG_DATA_HOME/gdcli/` (default `~/.local/share/gdcli/`) | program (yup-oauth2 token storage, one file per account) | 0600, `accounts/` and `gdcli/` 0700 |
| `default` | `$XDG_DATA_HOME/gdcli/` | program (the email of the default account) | 0600 |
| `token.json` | `$XDG_DATA_HOME/gdcli/` | legacy (0.3.0), moved to `accounts/` by the first command of a newer version | 0600 |

Relative `XDG_*` values are ignored per the XDG specification (`paths.rs`, std only). `auth setup`, `auth login` and the one-time migration create missing directories.

## Scopes

One token per account covers all commands; `auth login` requests all three scopes at once. Smart notes and the account discovery (Drive `about.get` with `fields=user(emailAddress)`, accepted with `drive.readonly`) need no further scope.

| Scope | Used by | Why this one |
|---|---|---|
| `https://www.googleapis.com/auth/calendar.events.readonly` | `calendar *`, `meet list`, `meet get`, `meet notes`, `meet transcript` (the event lookup) | narrowest read-only scope that allows `events.list` and `events.get` |
| `https://www.googleapis.com/auth/meetings.space.readonly` | `meet get`, `meet notes`, `meet transcript` | allows `spaces.get`, `conferenceRecords.list`, participants, recordings, transcripts and smart notes (read only); `meetings.space.created` would only see spaces created by this app |
| `https://www.googleapis.com/auth/drive.readonly` | `docs get`, `meet notes`, `meet transcript` (the document export), the account discovery | `files.export` accepts `drive`, `drive.readonly` and `drive.file`; `drive.file` only covers files the app created or opened, so `drive.readonly` is the narrowest that works for arbitrary documents. `drive.meet.readonly` only covers files generated by Meet and is not requested |

yup-oauth2 stores tokens per requested scope set and treats a token for a superset as valid for a subset. `Google::send` therefore always asks the authenticator for the full `SCOPES` list, never for a per-call subset, so every request, whatever API it targets, uses the one stored token. Every token file therefore contains exactly one entry.

## Flows

- `gdcli auth login`: creates `accounts/` (0700) and a transient `accounts/.login-XXXXXX` containing `[]` (so no stored token is touched and the flow always runs), builds the authenticator on that file with `InstalledFlowReturnMethod::HTTPRedirect` and `force_account_selection(true)` and the `Terminal` flow delegate (a local loopback server on a random port; the delegate prints the authorization URL to stdout and opens the browser, see "Opening the browser"), waits for the redirect, exchanges the code, requests a token for `SCOPES`, asks Drive which account signed in, renames the file to `accounts/<email>.json` and prints `account:`, `status:` and `default:` (`accounts.md`). The browser must run on the machine where gdcli runs (or the loopback port must be forwarded).
- `gdcli auth setup`: prints `docs/setup.md` (embedded at compile time, so the text exists once in the repository), `Destination: <path>` (the exact destination) and the prompt `Path of the downloaded JSON (empty if already placed at the destination): `, reads the answer from stdin (trimmed, surrounding quotes removed, a leading `~/` expanded to the home directory), then validates and installs it (`src/auth/setup.rs`) and runs the login flow with the same `Terminal` delegate (`auth setup --no-browser` hands the same decision to its login; the wizard text is unchanged). An empty answer means the file is already at the destination; it is then only validated. Validation requires the `installed` section, i.e. an OAuth client of type "Desktop app"; `web` clients are rejected.
- `gdcli auth list` and `gdcli auth set-default <email>` never talk to Google except for the one-time migration (`accounts.md`).
- Every Google command builds the authenticator for the chosen account file with `InstalledFlowReturnMethod::Interactive` and a flow delegate (`NotLoggedIn`) whose `present_user_url` returns an error. yup-oauth2 only calls the delegate when it has no usable token (the file holds no token, or refresh failed), so these commands never start a browser flow, never open a listening socket and fail immediately with ``error: token retrieval failed: Invalid user input: no valid token for <email>: run `gdcli auth login` and choose that account`` (for the legacy file during a migration: ``no valid existing token: run `gdcli auth login` ``). (`Google::send` adds the `token retrieval failed:` context to yup-oauth2's `Invalid user input: ...`.) A refresh failure caused by a network outage produces the same message. Valid and refreshable tokens work transparently; refreshed tokens are written back to the account file.
- Missing client secret: ``error: cannot read client secret <path>: run `gdcli auth setup`: No such file or directory (os error 2)``. It is reported before any account problem.

## Opening the browser

`auth login` and `auth setup` (which ends in the same login) print the authorization URL once and, unless told otherwise, open it in the default browser of the machine. One pure function decides once per run, `auth::browser::launch(no_browser, env)`, from the `--no-browser` flag and the environment (`lib.rs` passes `std::env::var_os`, tests pass a lookup closure and never mutate the process environment). The first matching row wins:

| # | Condition | Result | Opens | Hint line | URL line |
|---|---|---|---|---|---|
| 1 | `--no-browser` | `Skip` | no | no | once |
| 2 | `GDCLI_OPEN_BROWSER` equals exactly `1` | `Open` | yes | no | once |
| 3 | any variable of the list below set and not empty | `SkipWithHint` | no | once, before the URL | once |
| 4 | otherwise | `Open` | yes | no | once |

- `GDCLI_OPEN_BROWSER`: only the value `1` opts in; unset, empty, `0`, `true`, `yes` and `1 ` count as unset and never force "closed" (only the flag does). Outside an agent shell it changes nothing. The flag beats the variable and prints no hint. Agents set it only after the user has agreed to a browser opening on their machine, never on their own initiative (`SKILL.md`, `references/auth.md`).
- Streams: the hint and the URL line go to stdout (the stream of the URL line since 0.1.0), the hint first, through one writer owned by the delegate, so the order is fixed. The URL line is unchanged: `Please direct your browser to <url> and follow the instructions displayed there.` The hint is one line: `No browser was opened because an AI agent environment was detected. Set GDCLI_OPEN_BROWSER=1 only after the user has agreed to a browser opening on their machine, never on your own; otherwise pass --no-browser and hand the printed URL to the user.`
- `Terminal` (`src/auth/browser.rs`) is yup-oauth2's `InstalledFlowDelegate` for the login. yup-oauth2 12.1.2 calls `present_user_url` exactly once, with `need_code = false` (the `HTTPRedirect` flow, the only one the login uses), after the loopback server is bound, and ignores the returned code and any error (`let _ =`), so a delegate cannot fail a login; `Terminal` ignores `need_code` and returns an empty code. It prints (hint if any, then the URL line), then opens the browser when the decision is `Open`. Printing comes first, so a slow opener never delays the URL. Write errors are ignored; a poisoned lock is unreachable (release builds abort on panic and no writer panics). The yup-oauth2 default delegate did the same `println!` of the same line, which is why the URL line did not change.
- Scheme guard: the opener is called only for URLs starting with `https://`, case-sensitive. The URL is `auth_uri` of the user's `client_secret.json` plus a query, and `xdg-open` would act on `file:` or custom schemes; `HTTPS://...` is printed but not opened (Google's `auth_uri` is lowercase). A failing opener prints nothing more and is never an error.
- The opener is the `open` crate (5.4.5), `open::that_detached(url)`; the choice and the rejected crates are in `dependencies.md`. Behaviour on Linux, measured with stub launchers on `PATH` that only record their arguments (no real launcher ran): `xdg-open` exit 0 gives one call with exactly the printed URL; `xdg-open` exit 1 then `gio` exit 0 gives two calls; all of `xdg-open`, `gio open`, `gnome-open`, `kde-open6`, `kde-open5` and `kde-open` failing gives six calls in that order and no output; no launcher at all gives no call, no hang and only the URL on stdout; noise of a launcher on its stdout or stderr never reaches gdcli's streams; the crate ignores `$BROWSER`; a launcher such as `xdg-open` may read it (the environment is inherited). Launchers get null stdio and their own session (`setsid`), the crate waits at most 250 ms per launcher and reaps the child in a thread, so a launcher cannot take the terminal or block the login. On WSL (detected from `/proc`) PowerShell is tried first; SSH sessions get no special handling. `xdg-open` 1.2.1 itself falls back to `www-browser:links2:elinks:links:lynx:w3m` when no `$BROWSER` is set (lines 1094-1103 of the script); a text browser started that way has null stdio and cannot take the terminal (read from the source, not executed: no text browser exists on the development host).
- No display check: gdcli never looks at `DISPLAY` or `WAYLAND_DISPLAY`. WSL without WSLg and macOS have no `DISPLAY` and can still open a browser, so the behaviour of the crate is kept.

Not used, and why:

- `CLAUDE_CODE`: not in Claude Code's documentation, it appears only in third-party lists, so it cannot be verified.
- `CLAUDECODE`: documented, but IDE extensions also set it in the human's integrated terminals, which would block the human's browser.
- `OPENCODE_TERMINAL`: real, but OpenCode's `packages/core/src/pty.ts` sets it for the human's terminal panel as well as in agent shells.
- `AGENT`: a generic name; the mise crate ignores it as ambiguous, and OpenCode and goose also set `AI_AGENT` and `GOOSE_TERMINAL`.
- `CURSOR_TRACE_ID`: set for humans in Cursor terminals. `COPILOT_*`: user-set switches. `REPL_ID`: set in every Repl.
- `AMP_CURRENT_THREAD_ID` and the Kiro, Pi and Devin markers: found only in third-party lists or heuristics (`TERM_PROGRAM` without a tty, a `PATH` segment, `/opt/.devin`). Hermes (`NousResearch/hermes-agent`) bridges `HERMES_SESSION_*` only in gateway sessions and sets `HERMES_HOME`: no unconditional marker.
- Generic signals (`CI=true`, `TERM=dumb`, no tty on stdin or stderr) are not used: only agent variables count, and a human with redirected stdin must still get a browser.
- Undetected agents (Hermes and Amp included, Claude Code before v2.1.172) are told by `SKILL.md` to pass `--no-browser`.
- No crate: `mise-agent-env` 2026.10.1 (jdx/mise repository, no dependencies, `forbid(unsafe_code)`, but 9.7k downloads, created 2026-09-12, 4 reverse dependencies, date versions that follow mise's monthly releases, heuristics on `PAGER` and `PS1`), `is-ai-agent` (5 stars, 32k downloads in 90 days), `detect-coding-agent` (4 stars), `agent-detector` (3), `ai_env` (5) and `franken-agent-detection` (15) all fail the fame threshold of `dependencies.md` (500k downloads in 90 days or 100 reverse dependencies). The Vercel list exists only in JavaScript and Go. Exit plan: switch to a crate that meets the thresholds.

## HTTP stack for OAuth

yup-oauth2 is given a client built by gdcli (`CustomHyperClientBuilder`) with the same rustls connector as the API calls (ring crypto provider, bundled webpki root certificates). Its default client would scan the system certificate store.

## Refresh tokens

- The authorization URL carries `access_type=offline`. Google only returns a refresh token on the first consent of a user for a client; a repeated authorization without `prompt=consent` returns an access token only, which would leave gdcli unable to refresh after one hour. `force_account_selection(true)` makes yup-oauth2 add `prompt=select_account+consent` (yup-oauth2 `installed.rs`), so every `gdcli auth login` yields a refresh token and shows the account chooser. Google commands never build a flow URL, so they do not set it. A test starts the real binary and checks the printed URL.
- An OAuth consent screen in publishing status "Testing" issues refresh tokens that expire after 7 days. Publish the app ("In production"; unverified is fine for personal use, Google shows an unverified-app warning during login) or run `gdcli auth login` again. This is also written in `docs/setup.md`.
- Google commands create no directories: `$XDG_DATA_HOME/gdcli` and `accounts/` are created by `auth login`, `auth setup` and the one-time migration only.
