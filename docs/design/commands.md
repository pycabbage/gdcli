# Commands and output formats

Usage lives in the agent skill, not here: `skills/gdcli/` (printed by `gdcli skills`, design in `skills.md`) is the single source of truth for every command, option, range, default, column, record key, example and message that an agent needs. This file keeps what the skill does not carry: the rules shared by all commands, the selection algorithms, the flows, the observed facts behind them, the `update` details and the error text rules.

All output is plain UTF-8 text on stdout (or JSON with `--json`), designed to be cheap for LLM agents to read. Errors go to stderr as `error: <message>` with exit status 1; usage errors exit with 2. Nothing is printed to stdout on failure.

Common rules:

- One model, two renderings. Every `get` command (and `docs metadata`) builds ONE ordered record (a JSON object, key order is part of the contract) with our own snake_case names, empty values removed. `--json` prints that record on one line; the text rendering is one generic function over the same record, so both carry exactly the same information (the tests compare every text line with the record, including `false` values). Text rules: a top-level scalar is `key: value`; an array of scalars prints one `key: value` line per element with the singular key (the array key without its trailing `s`: `recurrence` stays, `attendees` gives `attendee:`); an array element that is an object, and a nested object value (`organizer`), print ONE line `key: name=value name=value ...` with every scalar leaf as a `name=value` pair in field order, using exactly the JSON field names, so no value is ever positional; a value is bare unless it is empty or contains whitespace, `"` or `=`, in which case it is JSON-quoted (`name="Dr. Bee"`); numbers and booleans print as they are (`index=0`, `optional=false`; `false` is never dropped); arrays nested inside an array element print after its line, with their own singular keys; records have at most one level of nesting inside array elements and objects, and an object nested deeper (which no record produces today) is never dropped but printed as one quoted JSON string value (`inner="{\"b\":\"x y\"}"`); an empty array prints `key: none` (singular key); multi-line top-level scalars (CR and CRLF are normalised to LF) continue on the following lines indented by two spaces; null and empty values never appear.
- List commands (`calendar list`, `meet list`, `auth list`) print a header line first (always, also when there are no items; a static string, the same number of tab-separated columns as every row), then one tab-separated line per item. `calendar list` and `meet list` are chronological ascending (oldest first); in default mode all past items come before all upcoming items, in range mode (`--from`) the rows are ordered by start time only; `auth list` has no past or upcoming grouping, its rows are sorted by email. Tabs, CR and LF inside values are replaced by a space. Missing values are empty columns (a row may end with a tab when its last column is empty). If the API calls fail, nothing is printed, not even the header. With `--json` the output is one JSON array of objects whose keys are exactly the header column names (all values strings), same rows, same order; no items print `[]` (`auth list` has no `--json`).
- JSON is compact (no pretty printing) and ends with one newline.
- `id` is the FIRST column of every list row, it is always the Calendar event id (the occurrence id returned with `singleEvents=true`: unique per occurrence and in the same format for past and upcoming rows), and it is the argument of `gdcli calendar get <id>`, `gdcli meet get <id>`, `gdcli meet notes <id>` and `gdcli meet transcript <id>`. Both list commands read only the Calendar API; the Meet REST API is used only by `meet get`.
- Why the Calendar event is the identity: Meet has no object for future meetings, and a conference record carries no link to the calendar event or occurrence it was started from. The Calendar event is therefore the only identity that exists for both past and upcoming meetings. Known limitation: ad-hoc meetings that were started without a calendar event are not listed.
- Time options: `--from` and `--to` of the list commands take `YYYY-MM-DD` (00:00:00 UTC of that day) or an RFC 3339 time with any offset (converted to UTC, whole seconds); one parser, `cli::moment`; anything else (`2026-11-31`, `2026-1-5`, a time without offset) is `invalid value '<x>' for '--from <TIME>': use YYYY-MM-DD or RFC 3339` (exit status 2). A day in another time zone is written `2026-11-20T00:00:00+09:00`.
- Timestamps: timed events are printed as RFC 3339 in UTC with second precision (`2026-11-18T09:30:00Z`) in lists and in `calendar get`/`meet get`; all-day events as their plain local calendar date (`2026-11-20`, not a UTC instant); Meet timestamps of conference records, participants and artifacts and the Drive times of `docs metadata` are passed through exactly as the API returns them. `docs get` prints Google's export bytes unchanged (no trailing newline is added).
- A closed output pipe (`gdcli calendar list | head -1`) ends the command quietly with exit status 0 and no message. Only an I/O error of kind `BrokenPipe` raised directly by writing the output counts; a broken pipe inside a network error is a normal error.
- ID arguments: `calendar get`, `meet get`, `meet notes` and `meet transcript` take an event id; clap rejects an empty id, `.`, `..` and any id containing `/ ? # %` with `invalid event id` (exit status 2) before any request is built. `docs get` and `docs metadata` take a document id or docs URL; an empty id, `.` and `..` are rejected with `invalid document id` (exit status 2).
- `--json` exists on exactly `calendar list`, `calendar get`, `meet list`, `meet get` and `docs metadata`. It does not exist on `auth *` (labeled lines or a table), `update`, `docs get`, `meet notes` or `meet transcript`: the option is allowed only when no official Markdown API exists, and Drive `files.export` is the official Markdown API (the two Meet commands print documents exported through it).
- `--account <email>` (`-a`; `cli::AccountArg`, flattened into the arguments) exists on exactly the eight Google leaf commands `calendar list|get`, `meet list|get|notes|transcript` and `docs get|metadata`, and nowhere else: not on `auth *` (they manage accounts), not on `update` (it talks to GitHub and never reads credentials; an option that does nothing would lie). Help text: `Google account (email) to use instead of the default`. The value is validated by the parser (`invalid value 'bad' for '--account <EMAIL>': expected an email address such as name@example.com`, exit status 2) and lowercased. Resolution order and the account errors: `accounts.md`.
- Timeouts: connecting to a Google or GitHub host fails after 10 s, and every command except `auth setup` and `auth login` (which wait for the user) fails with `error: timed out after 120s` when it has not finished after 120 s; inside `auth login` the migration of an old token and the identification of the new account are each bounded by the same 120 s.
- `fields` partial responses are sent on every JSON request, so only the printed data is transferred.

Error text: every message is built from our own lowercase context (`cannot ...`, `token retrieval failed: ...`, `google api error ...`, `request failed: ...`), so the first character is lowercase by construction and no formatting helper exists; a binary-level test checks the real stderr. Google API errors print as `google api error <status>: <message>` when the response carries a JSON `error.message` (cut at 300 characters, `...` appended), and as `google api error <status> <reason>` (for example `google api error 429 Too Many Requests`) otherwise, for Calendar, Drive, Docs and Meet alike. A successful answer that is not JSON prints `unexpected google api response: <parse error>`. Raw response bodies, headers and debug dumps are never printed. The account messages (``no account is logged in: run `gdcli auth login` ``, `unknown account ...`, `no default account; ...`, `cannot identify the account: ...`, the token messages that name the account) are listed in `accounts.md`, the `meet notes` and `meet transcript` messages are in `skills/gdcli/references/meet.md` and `invalid range` is described under the list commands; every hint names `gdcli auth login` or `gdcli auth setup` (0.3.0 said `gdcli login` and `gdcli setup`).

## `gdcli auth setup|login|list|set-default`

Usage: `skills/gdcli/references/auth.md`. Design: `accounts.md` (layout, selection, migration, the Drive dependency, the messages) and `auth.md` (the OAuth client, scopes, flows). `auth list` is a list command (header `account<TAB>default`, rows sorted by email, no `--json`, no past or upcoming grouping); `auth login` and `auth set-default` print `output::record` lines; there is no top-level `gdcli set-default`. `auth setup` and `auth login` take exactly one option, `--no-browser` (`cli::LoginArgs`, the same struct for both; help: `Do not open a browser, only print the login URL (the default in an AI agent shell; GDCLI_OPEN_BROWSER=1 opens it there)`), and both show the environment variable `GDCLI_OPEN_BROWSER` in `after_help`; they are the only commands that start a browser. Without the flag the login URL is printed once and opened through the `open` crate; in an AI agent shell nothing is opened and one hint line precedes the URL unless `GDCLI_OPEN_BROWSER=1`. The decision table, the variable list with sources, the hint and the opener behaviour: `auth.md` ("Opening the browser"). The option does not exist on any other command (a test pins it).

## `gdcli update`

Replaces the running executable with the latest GitHub release of `pycabbage/gdcli` (design, security level and bounds: `update.md`). No arguments and no options (`update --json` and `update x` are usage errors, exit status 2; there is no `--json` because the output is three labeled lines and `--json` is listed only for the commands above). It needs no Google credentials and never reads or writes the config or data directories. The optional environment variable `GITHUB_TOKEN` (non-empty) is sent as `Authorization: Bearer <token>` on the request for the latest release only (never on the download), which raises the GitHub rate limit from 60 requests per hour per IP to 5,000 per hour per user; `GH_TOKEN`, a flag or a file are not supported (rules and reasons: `update.md`).

Output on stdout, exit status 0, rendered by `output::record` (keys always `status`, `current`, `latest`):

```
status: updated
current: 0.1.1
latest: 0.2.0
```

```
status: up_to_date
current: 0.2.0
latest: 0.2.0
```

- `updated`: the replacement succeeded; the next start of `gdcli` is `latest`; `current` is the version that ran the command.
- `up_to_date`: `latest <= current` (a development build newer than the release prints both values). One API request, nothing written.
- Nothing is printed to stdout on failure; stderr gets `error: <message>` and the exit status is 1.

| Situation | stderr |
|---|---|
| DNS, connect, TLS or transport failure | `error: request failed: <error chain>` |
| 120 s deadline | `error: timed out after 120s` |
| 403 or 429 with `x-ratelimit-remaining: 0`, no token sent | `error: github api rate limit exceeded; resets at 2026-11-19T01:36:49Z; set GITHUB_TOKEN to raise the limit of 60 requests per hour` (from `x-ratelimit-reset`; without a usable reset header the `; resets at ...` part is absent) |
| the same with a token sent | `error: github api rate limit of the GITHUB_TOKEN exceeded; resets at 2026-11-19T01:36:49Z` (without a usable reset header the `; resets at ...` part is absent) |
| `GITHUB_TOKEN` is not a valid HTTP header value (before any request) | `error: GITHUB_TOKEN is not a valid HTTP header value` |
| 401 on the latest-release request when the token was sent with it | `error: github rejected GITHUB_TOKEN (401): unset it or provide a valid token` |
| 404 on the latest-release URL (no published release) | `error: github has no published release for pycabbage/gdcli` |
| any other non-2xx status, including a 3xx without a usable `Location` and a 401 on any request that carried no token (none configured, the redirect chain left the API host, or the archive download), on any URL | `error: github api error <status>` with the status as `http::StatusCode` prints it, for example `github api error 404 Not Found` |
| the API body is not JSON | `error: unexpected github api response: <parse error>` |
| tag missing or not `v<major>.<minor>.<patch>` | `error: latest release tag "x" is not v<major>.<minor>.<patch>` |
| tag with a prerelease part | `error: latest release v1.0.0-rc.1 is a prerelease and is not installed` |
| release not immutable | `error: release v0.2.0 is not immutable and is not installed` |
| no asset for this platform | `error: release v0.2.0 has no asset gdcli_linux_riscv64.tar.gz` |
| asset without URL or without a `sha256:` digest | `error: asset gdcli_linux_x86_64.tar.gz has no download url or sha256 digest` |
| install directory not writable (checked before the download) | `error: cannot write to /usr/bin: Permission denied (os error 13)` |
| host, scheme, port or userinfo not allowed (first URL or a redirect) | `error: refusing to fetch from unexpected host or scheme https://example.com` (scheme and host only) |
| `browser_download_url` is not a URL | `error: invalid download url: <parse error>` |
| more than 3 redirects | `error: too many redirects` |
| the response body breaks while downloading | `error: download failed: <error chain>` |
| writing the download to the staging file fails (for example a full disk) | `error: cannot write the download: <io error>` |
| download over the limit | `error: download exceeds 33554432 bytes` |
| digest differs | `error: checksum mismatch: expected <64 hex>, got <64 hex>` |
| gzip or tar damaged, the inflated stream exceeds four times the limit, or creating or writing the extracted binary fails (for example a full disk) | `error: cannot extract the archive: <io error>` |
| no regular file named exactly `gdcli` (also: it is a symlink or a directory, or the inflated stream was cut at an entry boundary) | `error: archive has no regular file named gdcli` |
| entry `gdcli` over the limit | `error: archive entry gdcli is larger than 33554432 bytes` |
| the replacement itself fails | `error: cannot replace the executable in /usr/bin: <io error>` |
| the location of the running executable cannot be determined | `error: cannot locate the running executable` |

## `gdcli calendar list`

Usage and columns: `skills/gdcli/references/calendar.md`. Primary calendar, two modes. Default mode: `--past N` and `--upcoming N` (alias `--future`) choose how many items of each side are fetched: default 5 each, accepted range 0 to 1000 (clap rejects the rest with exit status 2). `0` skips that side entirely: no request is made for it. Memory stays bounded by N (a ring buffer of N for the past side, N collected events for the upcoming side). Range mode (`--from`): see "Range mode and `--query`" below. The header line is `events::CALENDAR_HEADER` (and `events::MEET_HEADER` for `meet list`), the only copy of the text; the JSON keys are the header names.

Selection (the two lookups run concurrently; one implementation, `events::list`, shared with `meet list` and parameterised by a predicate):

- Every `events.list` request carries `eventTypes=default&eventTypes=focusTime&eventTypes=outOfOffice&eventTypes=fromGmail` (the parameter is repeated). Working-location and birthday events are not appointments and would drown the list (for a real account about half of the all-day entries were working locations).
- Upcoming (`events::first`, shared with range mode): `singleEvents=true`, `orderBy=startTime`, `timeMin=now`, `maxResults=min(N, 250)`; pages continue until N non-cancelled, not yet ended events that match the predicate are collected or the calendar is exhausted. `timeMin` filters on the event end, so an event that is running now is an upcoming event.
- Past: the API cannot sort descending, so the newest past events are found by searching backwards over nested windows `[now - w, now)` for `w` = 7, 30, 180 and 730 days (`timeMax=now`, `orderBy=startTime`, `maxResults=250`). Within a window all pages are read, the predicate is applied first, and only the last N events that have ended (`end <= now`, not cancelled) are kept in a ring buffer. The search stops at the first window that yields N events; if even the 730 day window has fewer, those are printed.
- An event is in exactly one group: `end <= now` is past, otherwise upcoming; both groups drop events on the other side of that line (so a server answer that disagrees with the client clock cannot print an event twice) and cancelled events. All-day events are treated as ending at 00:00 UTC of their exclusive end date, while the server filters `timeMin`/`timeMax` in the calendar's time zone, so in time zones ahead of UTC an all-day event can be absent from both lists for a few hours around its end. The time zone is not requested to correct this. The `when` column is computed from the event itself (`end <= now` is `past`), which is the same decision in both modes.

Range mode and `--query` (shared by `calendar list` and `meet list`):

- `--from <TIME>` starts range mode, `--to <TIME>` bounds it, `--query <TEXT>` filters (both modes), `--limit <N>` (1 to 1000, default 50) caps the rows. `--from` conflicts with `--past` and `--upcoming`; `--to` and `--limit` require `--from` and also conflict with an explicit `--past` or `--upcoming` (without that conflict clap would suppress the missing `--from` error whenever `--past` or `--upcoming` is given, and the option would be ignored silently); `--query` composes with both modes. The help texts say `First N matches, oldest first (range mode, default 50)` and `Range mode: only events ending after this time`.
- The range is the set of events that overlap `[from, to)`: `timeMin` is the exclusive lower bound of the event END and `timeMax` the exclusive upper bound of the event START; `--from` alone sends no `timeMax`. The request is the default-mode request (`singleEvents=true`, `orderBy=startTime`, `fields`, the four `eventTypes`) plus `timeMin`, `timeMax`, `q` and `pageToken`, with `maxResults=min(limit, 250)` for `calendar list` and 250 for `meet list` (the Meet predicate drops most events, so large pages find the first matches sooner).
- The rows are the first `--limit` non-cancelled events that match the predicate, oldest first (the server order), so `--limit 5` is the five oldest matches, not the newest. Paging stops as soon as the limit is reached, so requests and memory are bounded by the limit (at most 1000 events and one page). Exactly N rows can mean that more matches exist; no marker line is printed. `when` is `past` when `end <= now` and `upcoming` otherwise, so a running long event can precede a shorter past event.
- `--query` is sent as the Calendar `q` parameter (free text over title, description, location, and attendee and organizer names and emails, case-insensitive on Google's side, percent-encoded by the URL builder) on every `events.list` request. In range mode it filters the range. In default mode it is added to both sides and to every nested past window and every page, so the lists are the latest N matches; the past search can look back at most 730 days (the widest window), so `--query standup --past 10 --upcoming 0` is the latest 10 matches of the last 730 days and older matches need `--from`. A blank query is rejected by the value parser (`invalid query: it must not be blank`, exit status 2), like a blank `--tab`.
- `ListArgs::check()` runs first in the `calendar list` and `meet list` arms of `lib.rs`, before the client secret is read and before any request: `--from` must be earlier than `--to`, compared in whole seconds like the request (`00:00:00.1Z` to `00:00:00.9Z` would send equal `timeMin` and `timeMax`, which Calendar answers with a 400), else `invalid range: --from must be earlier than --to` (exit status 1, nothing printed). Header, columns and `--json` are the same in both modes; a range without events prints the header alone (`[]` with `--json`).

## `gdcli calendar get`

`events.get` on the primary calendar with a `fields` mask; the record (keys, order, meaning) is in `skills/gdcli/references/calendar.md`. Design facts: `meeting_code` is set only for a `hangoutsMeet` conference, `conference_id` only for another conference type; `meeting_uri` is the `hangoutLink`, else `https://meet.google.com/<meeting_code>`; `attendees[].optional` is kept only when true; `attachments(title,mimeType,fileId)` is in the mask (`fileUrl` and `iconLink` are not requested) and the text form is `attachment: title="Notes by Gemini" mime_type=application/vnd.google-apps.document file_id=1AbCdEf`; a Google Doc `file_id` works with `docs get` and `docs metadata`; the description comes last because it may span lines.

## `gdcli meet list`

Usage and columns: `skills/gdcli/references/meet.md`. It is `calendar list` restricted to events that carry a Google Meet link (`conferenceData.conferenceSolution.key.type == hangoutsMeet`, not cancelled), with the extra column `meeting_code` (`conferenceData.conferenceId`). The count options, range mode and `--query` work as in `calendar list`; for Meet the upcoming page size stays 25 and the page size of range mode is 250.

Same selection rules as `calendar list` (past = ended, a running meeting counts as upcoming, cancelled events dropped, no duplicates, nested past windows with the predicate applied before the N element ring buffer). The `fields` mask adds `conferenceData(conferenceId,conferenceSolution(key(type)))` to the calendar mask. The Meet REST API is not called, so the list needs no Meet scope or Meet API access.

## `gdcli meet get`

The argument is the event id printed by `meet list` or `calendar list`; nothing else is accepted (no meeting codes, no conference record ids). Record keys and examples: `skills/gdcli/references/meet.md`. Flow:

1. `events.get` of the event (`fields=id,summary,start,end,conferenceData(...),attachments(title,mimeType,fileId)`). If it has no Google Meet conference the command fails with `event <id> has no google meet conference`.
2. Concurrently: `spaces.get` of `spaces/<meeting code>` and `conferenceRecords.list` (`pageSize=5`, newest first) with the filter `space.meeting_code = "<code>" AND start_time>="<event start - 1h>" AND start_time<="<event end + 1h>"` (RFC 3339 UTC with milliseconds; the Meet filter grammar documents `AND` and `start_time` comparisons). A meeting code is shared by every occurrence of a recurring event, so the time window selects the occurrence; the slack is the constant `SLACK_HOURS`. All-day events (and events without date-times) use only the meeting code.
3. For each returned conference record (typically one), concurrently: participants (`pageSize=250`), recordings, transcripts and Gemini smart notes (`smartNotes.list`, `pageSize=100`, `fields=smartNotes(state,startTime,endTime,docsDestination/document)`; GA since 2026-04-02, covered by the scopes already requested), four requests on the same HTTP/2 connection.

Record: the keys follow the order of the `json!` literals in `meet::get` and `records::conferences`; `access_type`, `entry_point_access` and `moderation` come from the Meet space `config` (Google withholds it for spaces the account does not own, then the keys are absent); `attachments` sits after the space settings and before `conferences`; `conferences` (oldest first, one object per conference record) is present, possibly empty, when the record list succeeded and absent when that call failed; an empty `conferences` array prints `conference: none`; an empty `end` of a conference means it is still running; `meet_api` is `unavailable (<code> <google message>)` and only present when a Meet call answered 403 or 404. The artifacts of a conference are `participants` (`kind` is `user`, `anonymous` or `phone`), `recordings`, `transcripts` and `smart_notes` (both with `document_id`, the input of `docs get`, `meet transcript` and `meet notes`).

Meet 403 or 404 answers are tolerated per call (space, conference list, participants, recordings, transcripts, smart notes, for example a meeting organised by someone else): everything that did arrive is printed, followed by the `meet_api` entry (the first failure), and the exit status is 0. Every other error is a normal error and nothing is printed. What Meet answers for `smartNotes.list` on an account or a meeting without Gemini notes (an empty list, 403 or 404) is not known from documentation; every form is tolerated and an empty list gives no `smart_notes` key.

## `gdcli meet notes` and `gdcli meet transcript`

Print the Gemini notes document (`meet notes`) or the transcript document (`meet transcript`) of a meeting as Markdown. `<id>` is the event id of `meet get`. No `--json` (the output is Google's Markdown export). Only Meet artifacts are used (there is no fallback to the event attachments, whose titles are localized): `smartNotes` for notes, `transcripts` for the transcript, items in state `FILE_GENERATED` that carry a document id. Meet keeps a conference record only from the start of a meeting until 30 days after it, so an upcoming meeting and a meeting older than 30 days have none: read those with the `attachment:` lines of `calendar get` and `docs get <file_id>`. Flow (all requests sequential, Bearer token, no retry, no polling):

1. `events.get` with the same `fields` mask as `meet get`; no Meet conference is `event <id> has no google meet conference`.
2. `conferenceRecords.list` (`pageSize=5`, the filter of `meet get`: meeting code plus the event window with one hour of slack). Unlike `meet get`, 403 and 404 are errors here and nothing is tolerated. `spaces.get` is never called.
3. For each record, oldest first (the API answers newest first), one `smartNotes` or `transcripts` request (`pageSize=100`, the mask of `meet get`, first page only). Items that are not `FILE_GENERATED` or have no document id are ignored; their state (the last one seen, which belongs to the newest record) is remembered for the error below.
4. For each ready document, in that order, the response of `docs::response` (the code of `docs get`: Drive `files.export` with `mimeType=text/markdown`, or with `--tab` the tab list, client-side tab resolution and the Docs web export, `docs get --tab` below). All responses are opened before the first byte is written, so a refused document, a status error or an unknown tab prints nothing and fails with exit status 1; a body that breaks mid-stream behaves like `docs get` (partial output, then `error:`).
5. One document: its Markdown only, byte-identical to `docs get <document_id>` (with `--tab`: to `docs get <document_id> --tab TAB`). Several documents (several records, or several items of one record): each is preceded by the line `document: id=<document id> start=<start> end=<end>` (times as Meet returns them) and followed by two newlines, because the export has no trailing newline; so the output is no longer pure Markdown and agents must not assume it is.

`--tab` is the `docs get` parser and resolution. A Gemini notes document has the notes tab and, when the meeting was transcribed into the same document, a second tab with the transcript, so one or two tabs (measured, see the paragraph on the transcript below). Tab titles are localized and not a contract: Google's English help page describes notes documents with tabs named `Quick notes` and `Full notes`, other variants and locales may differ, and the first tab of the measured account had another title. List the tabs with `gdcli docs metadata <document_id>` (`tab:` lines) and pass a tab id (`t.abc`) or a title to `--tab` (both select the same tab and return the same bytes). Without `--tab` the whole export contains every tab, but it is not the byte concatenation of the per-tab exports (measured: 29,559 B whole against 9,451 B plus 20,557 B for the two tabs), so do not join per-tab exports and expect the whole export. For a document with a single tab the whole export and the export of its only tab differ only by the per-tab formatting differences (measured: 8,506 B against 8,495 B; `docs get` below).

Where the transcript lives, measured with the shipped `v0.4.0` binary on 2026-11-20 (copies of the installed credentials, counts only; the tab structure read with `docs metadata` through the Docs API, no web exports): of the 8 most recent meet events that have a generated smart note, in 6 the transcript document id equals the smart-note (notes) document id, and each of those documents has exactly 2 tabs, exactly one of which is a transcript tab (its title matched the localized word for transcript, `ranscript` or its Japanese equivalent); in the other 2 there is no transcript, and the notes document has 1 tab. In an older event the notes (8,506 B) and the transcript (58,131 B) were separate documents. A transcript is therefore a tab of the notes document in some meetings and a separate document in others (it varies between meetings of the one measured account; other accounts and settings were not measured). Both commands print the whole document with every tab unless `--tab` is given, so in the shared case `meet notes` and `meet transcript` print the same bytes (17,219 B for the event checked with the export) and `--tab` with the notes tab id or the transcript tab id selects one part (list the tabs with `gdcli docs metadata <document_id>`). The commands do not detect or special-case this and there is no behavior change. The skill (`skills/gdcli/references/meet.md` and step 3 of `SKILL.md`) says so from the release after `v0.4.0` on; the `v0.4.0` binary embeds the earlier text.

Failure behaviour (the message texts are in `skills/gdcli/references/meet.md`): every failure is an error with exit status 1 and an empty stdout, and nothing is retried or polled. 403 and 404 on the conference record list, on an artifact list and on a document export are errors here, not tolerated as in `meet get` (a 404 is possible on an export, because Drive may hide a file the account cannot see). All exports are opened before the first byte is written, so a refused document, a status error or an unknown `--tab` prints nothing. An export or `--tab` error is wrapped with a context that names the label (`gemini notes document` for `meet notes`, `transcript` for `meet transcript`) and the document id, and the `docs get --tab` messages follow it.

Records of a recurring event are selected like in `meet get` (meeting code plus the event window), so an occurrence yields its own records; an event without date-times filters by meeting code only and may return documents of other occurrences (the same limit exists in `meet get`). Only the first page of records (5) and of artifacts (100) is read.

## `gdcli docs get`

The argument is a document id or any URL containing `/d/<id>` (`document_id` cuts it at the next `/`, `?` or `#`; the `tab=` of a pasted URL is ignored, use `--tab`). There is no `--json`: the document is exported as Markdown by Google itself, which is the official Markdown API, so no conversion is implemented.

- Without `--tab`: Drive `files.export` with `mimeType=text/markdown`, the whole document; the export contains every tab one after another, with no tab titles and no separator added by gdcli, but it is not the byte concatenation of the per-tab exports (below). The response body is copied to stdout chunk by chunk as it arrives. Google limits exported content to 10 MB; larger documents fail with the API's `exportSizeLimitExceeded` message.
- With `--tab <TAB>`: one tab only. No official API exports a single tab as Markdown (Drive `files.export` has only `mimeType`; a `tab=` parameter there is silently ignored). gdcli therefore (1) lists the tabs with the Docs API, (2) resolves `<TAB>` client-side, and (3) requests the Docs web export `https://docs.google.com/document/d/<id>/export?format=md&tab=<tabId>`. This is an explicit exception, pending owner sign-off, because the `tab=` export parameter is undocumented and could change; exit plan: own conversion from the Docs API JSON (about 300 lines).
  1. Tab list: `GET docs.googleapis.com/v1/documents/<id>?includeTabsContent=true&fields=tabs(P,childTabs(P,childTabs(P)))` with `P = tabProperties(tabId,title,index,parentTabId,nestingLevel)`; child tabs up to three levels are flattened in document order. Needs the Google Docs API enabled in the project (see `setup.md`); the drive.readonly token is accepted.
  2. Resolution, always client-side because Google silently returns the first tab for an unknown or unprefixed `tab=`: (a) exact tab id; (b) when the argument lacks the `t.` prefix, exact tab id `t.<argument>`; (c) exact title (case-sensitive); (d) case-insensitive title. The first step with exactly one match wins. More than one match in a step is an error that lists the candidates and never picks one (`tab "Notes" is ambiguous: t.bbb (Notes), t.ccc (Overview > Notes)`; the path shows the parent tabs); no match is `tab "x" not found; available: "A" (t.aaa), "B" (t.bbb)`. There is no `Parent/Child` syntax. The full resolved tab id is always sent.
  3. Export (observed live on a real account): the request carries `Authorization: Bearer`; Google answers 307 to a `https://doc-xx-docstext.googleusercontent.com/export/...` URL that is fetched WITHOUT the Authorization header. At most one redirect is followed, only to an `https` URL whose host ends with `.googleusercontent.com` (anything else, for example a login page, is `export redirected to an unexpected host`; the bearer token is never sent to the redirected host). The final response must have a content type starting with `text/markdown` or `text/x-markdown`, compared case-insensitively (else `unexpected export content type`, for example for `text/html`) and is streamed to stdout. The web export is rate limited: docs.google.com answers 429 (HTML) after roughly a dozen exports within a few minutes; the CLI prints `google api error 429 Too Many Requests` and does not retry.
  4. Observed facts (live check with a real account, 2026-11-18): the 307 target is `https://doc-xx-xx-docstext.googleusercontent.com/export/...?format=md&tab=...&dat=...` (host class `*.googleusercontent.com`); the final answer is `200` with `Content-Type: text/x-markdown; charset=utf-8` (not `text/markdown`; the body is valid Markdown) and a `Content-Disposition` header that carries the document title, which gdcli ignores. Per-tab Markdown differs from the whole-document export only in formatting: headings carry no `{#id}` anchors, internal links are tab-qualified (`(?tab=t.xxx#heading=h.xxx)`) instead of `(#MM:SS)`, and checkbox lists are loose (blank lines between items); the content is otherwise identical. Neither export ends with a newline. The whole-document export is not the byte concatenation of the tab exports: a live check on 2026-11-20 of a two-tab Gemini notes document measured 29,559 B for the whole export and 9,451 B plus 20,557 B (30,008 B) for the two tab exports; a single-tab document measured 8,506 B whole against 8,495 B for its only tab. `--tab` by title returns the same bytes as `--tab` by id.
  5. `--tab` must not be blank: clap rejects it with `invalid tab: it must not be blank` (exit status 2) before any request.

## `gdcli docs metadata`

Only the metadata of a Google Doc. Two calls run concurrently: Drive `files.get` (`supportsAllDrives=true`, `fields=id,name,mimeType,createdTime,modifiedTime,version,webViewLink,owners(displayName,emailAddress),lastModifyingUser(displayName,emailAddress),shared,trashed,starred,viewedByMeTime,modifiedByMeTime,parents,description`) and the Docs API tab list of `docs get --tab`. The file must be a Google Doc (`mimeType` `application/vnd.google-apps.document`), else `not a google doc (mimeType <x>)`. Record: keys, order and meaning are in `skills/gdcli/references/docs.md`. Times are passed through as Drive returns them. `parent_id` appears only on child tabs; `tabs_unavailable` replaces `tabs` when the Docs API call fails (for example the API is not enabled) and carries Google's short message, the command still succeeds.
