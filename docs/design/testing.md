# Testing

`cargo test` needs no credentials and no network access. Everything under `tests/` uses the library API or the built binary. 277 tests (accounts 31, auth 10, binary 19, browser 14, calendar_get 5, calendar_list 17, cli 20, docs 18, errors 11, meet 23, meet_read 12, range 15, secret 7, skills 16, units 30, update 29).

Testability design: command functions take the `Google` facade, the current time and the output writer as parameters; `Google::new` takes the two root URLs; the token source is yup-oauth2's `AccessTokenAuthenticator` in tests; `Paths::new` takes explicit directories; `auth::accounts::store`, `adopt` and `email` take a `&Google` (the mock in tests), `migrate` and `auth::login` are thin production glue over them, and `run_with(cli, resolve, out)` takes the path resolver and the output writer (`run` passes the locked stdout), so no production seam exists for accounts either; `update::run_with` takes the `Fetcher` (client and host predicate), the API URL, the `Install` (staging directory, replace function, size limit) and the writer, so no production-reachable seam exists (no environment variable, flag or Cargo feature) and `run` is the only place that names production values.

Not covered by the in-process tests: the real replacement of a running executable (ETXTBSY, rename, permission preservation, symlinked install, read-only directory) and the production wiring of `update::run`. They are proven by the real runs against the real GitHub release (the script in the verification checklist of `release.md`, run from a scratch directory outside the repository, builds scratch copies with versions 0.0.1, the latest release and 9.0.0 and checks digests, `--version`, mode, ownership, symlink, read-only directory, leftovers and peak RSS); the release procedure in `release.md` runs them before and after a release. It printed `E2E-OK` against the genuine `v0.2.0` release on 2026-11-19 and, with the invalid-token and empty-token cases added, against the genuine `v0.3.0` release on 2026-11-20; see docs/design/update.md.

Not covered by automated tests (needs real credentials or Google's servers): the interactive OAuth login against Google (the printed authorization URL is tested with the real binary; the account chooser, the redirect and the end of `auth login` need a browser and a human), the migration of a real 0.3.0 token (tested in-process with a mock Drive and with a corrupt legacy file), the 120 s bounds inside `auth login`, token refresh, real API payloads, the HTTP/2-only client and the 10 s connect timeout, and the line in `run_with()` that applies `deadline_for` (the pure function and `with_deadline` are tested; wiring them needs a command that hangs). During development the login URL and loopback server were exercised manually with a fake client id, and API calls with a bogus token (Google answered 401, proving TLS with the bundled roots, HTTP/2 and request routing for Calendar, Drive and Meet; `strace` showed one connection per command).

Not verifiable by agents (0.4.1): a real GUI browser opening (and the text-browser fallback of a headless `xdg-open`), the real OAuth consent and redirect, whether the shipped versions of the listed agents still set their variables (only live documentation and default-branch source were read; Cursor is closed source; Claude Code needs v2.1.172 or later) and `open` on macOS and WSL. The same mutant was deliberately not run on `tests/auth.rs`: without `PATH` glibc's `execvp` searches `/bin:/usr/bin`, which would find a real `xdg-open` for the stub tests.

Process and network check of the whole suite (0.4.1): the 18 test executables, run one by one as `strace -f -e trace=execve,connect -o <log> -- env -i HOME=<scratch>/home XDG_CONFIG_HOME=<scratch>/config XDG_DATA_HOME=<scratch>/data PATH=<scratch>/empty TMPDIR=<scratch>/tmp <test executable>`, all exit 0 and execute only `env`, the test executables, the gdcli binary (72 starts) and the recording `xdg-open` stub (3 starts, the three stub tests that expect an opening); no `execve` fails, no other launcher or program is started, and all 421 `connect` calls go to `127.0.0.1` (the mock servers and the loopback redirect servers).

The local toolchain must be the latest stable, because CI uses `@stable` and lints change between releases (`rustup update stable && rustup component add clippy rustfmt`; see `lints.md`). The local quality gates are `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings`, `cargo test` and `cargo build --release --locked`. CI (`.github/workflows/ci.yml`) runs fmt, clippy, build and test.
