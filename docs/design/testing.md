Testability design: command functions take the `Google` facade, the current time and the output writer as parameters; `Google::new` takes the two root URLs; the token source is yup-oauth2's `AccessTokenAuthenticator` in tests; `Paths::new` takes explicit directories; `auth::accounts::store`, `adopt` and `email` take a `&Google` (the mock in tests), `migrate` and `auth::login` are thin production glue over them, and `run_with(cli, resolve)` takes the path resolver, so no production seam exists for accounts either; `update::run_with` takes the `Fetcher` (client and host predicate), the API URL, the `Install` (staging directory, replace function, size limit) and the writer, so no production-reachable seam exists (no environment variable, flag or Cargo feature) and `run` is the only place that names production values.

Not covered by the in-process tests: the real replacement of a running executable (ETXTBSY, rename, permission preservation, symlinked install, read-only directory) and the production wiring of `update::run`. They are proven by the real runs against the real GitHub release (the script in the verification checklist of `release.md`, run from a scratch directory outside the repository, builds scratch copies with versions 0.0.1, the latest release and 9.0.0 and checks digests, `--version`, mode, ownership, symlink, read-only directory, leftovers and peak RSS); the release procedure in `release.md` runs them before and after a release. It printed `E2E-OK` against the genuine `v0.2.0` release on 2026-11-19 and, with the invalid-token and empty-token cases added, against the genuine `v0.3.0` release on 2026-11-20; see docs/design/update.md.

Not covered by automated tests (needs real credentials or Google's servers): the interactive OAuth login against Google (the printed authorization URL is tested with the real binary; the account chooser, the redirect and the end of `auth login` need a browser and a human), the migration of a real 0.3.0 token (tested in-process with a mock Drive and with a corrupt legacy file), the 120 s bounds inside `auth login`, token refresh, real API payloads, the HTTP/2-only client and the 10 s connect timeout, and the line in `run_with()` that applies `deadline_for` (the pure function and `with_deadline` are tested; wiring them needs a command that hangs). During development the login URL and loopback server were exercised manually with a fake client id, and API calls with a bogus token (Google answered 401, proving TLS with the bundled roots, HTTP/2 and request routing for Calendar, Drive and Meet; `strace` showed one connection per command).

Hermeticity rule: every binary test starts from `env_clear()`; the shared helper `gdcli()` in `tests/binary.rs` (and the spawn in `tests/auth.rs`) always sets `HOME` to a path inside the test's temporary directory, `isolated()` adds `XDG_CONFIG_HOME` and `XDG_DATA_HOME` inside it, and a test that exercises the XDG or `HOME` fallbacks overrides exactly the variables it examines. A test never leaves a parseable legacy `token.json` next to an empty `accounts/` (the migration would call the real Google API): a token that a test needs is placed under `accounts/`, and only as an expired token without a refresh token (it fails at the flow delegate without any request) or as garbage.

Rules for every agent (implementer, reviewer, end-to-end run) that runs a gdcli binary: it is run only as `env -i HOME=<scratch>/home XDG_CONFIG_HOME=<scratch>/config XDG_DATA_HOME=<scratch>/data PATH="$PATH" <binary> ...`, where `<scratch>` is a directory outside the repository (in the agent scratch area): empty, or for real-credential runs holding only the installed copies of the credential files, and removed on exit, whatever its origin (built from source, from a test directory or downloaded); never with the inherited environment and never with the owner's real directories as `HOME` or `XDG_*`. Credential files are copied only with `install -m 600 <src> <dst>` (silent) and never opened, printed, grepped or compared; reports contain counts, shapes, statuses, modes and truncated ids only, never emails, titles, document text or full ids. `cargo test` is allowed because every binary test follows the hermeticity rule.

Survivors: removing the 120 s deadline from the migration or from the account discovery inside `auth login` (the bound cannot be observed without waiting 120 s or a production seam; `with_deadline` and `deadline_for` have their own tests); moving `Command::Update` behind `resolve()` (`update::run` talks to GitHub and replaces the running executable, so no hermetic test can observe the order; checked by reading `lib.rs` and by running the mutant on a copy, where all tests still pass); and walking only the top-level error instead of the error chain when looking for the Google API status (equivalent today: the API error is the root error of the discovery call, so the chain walk only protects against a future `.context(..)` layer).

The local toolchain must be the latest stable, because CI uses `@stable` and lints change between releases (`rustup update stable && rustup component add clippy rustfmt`; see `lints.md`). The local quality gates are `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings`, `cargo test` and `cargo build --release --locked`. CI (`.github/workflows/ci.yml`) runs fmt, clippy, build and test.
