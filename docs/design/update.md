# `gdcli update`

`gdcli update` replaces the running executable with the latest release of `pycabbage/gdcli` on GitHub. The output records and the error messages are specified in `commands.md`; this file records the design, the security level and the evidence. The code is the module `src/update/`: `mod.rs` (138 lines: constants, `version`, `asset`, `Install`, `extract`, `run_with`, `run`) and `fetch.rs` (142 lines: everything that touches the network or the token: `github`, `github_token`, `bearer`, `Fetcher`).

## Flow

1. `GET https://api.github.com/repos/pycabbage/gdcli/releases/latest` (one request, `User-Agent: gdcli/<version>`, and `Authorization: Bearer <token>` when the environment variable `GITHUB_TOKEN` is set to a non-empty value; see GITHUB_TOKEN below).
2. The tag must be `v` plus a semver version without a prerelease part. If it is not greater than the running version (`CARGO_PKG_VERSION`) the command prints `status: up_to_date` and stops.
3. Otherwise the release must be immutable and contain the asset `gdcli_<OS>_<ARCH>.tar.gz` (`std::env::consts`, so `gdcli_linux_x86_64.tar.gz` and `gdcli_linux_aarch64.tar.gz`) with a download URL and a `sha256:` digest.
4. The first staging file is created in the install directory (the directory of `current_exe()`); a directory that is not writable fails here, before any download.
5. The asset is streamed into that unnamed file while its SHA-256 is computed; the digest must equal the one from the API before the archive is opened.
6. The tar.gz is read once: the entry named exactly `gdcli` that is a regular file is copied into a second staging file (`NamedTempFile` in the install directory).
7. `self_replace::self_replace` swaps the executable; the command prints `status: updated`.

## Version and release rules

- The tag is `v<major>.<minor>.<patch>`; anything else, and any prerelease part, is an error. A semver compare (`semver` crate) decides; `latest <= current` is up to date, so there is no downgrade and no reinstall.
- GitHub orders `releases/latest` by the creation time of the release (`created_at`), not by semver. Publish versions in increasing order; a backport published after a newer release makes `latest` smaller than the running version, which reports `up_to_date`.
- `.goreleaser.yaml` has `prerelease: auto` under `release:`, so GoReleaser marks a release whose tag has a semver prerelease suffix (`v1.0.0-rc1`) as a GitHub prerelease, and `releases/latest` excludes prereleases. Evidence (GoReleaser v2.20.2): `internal/pipe/release/release.go` lines 75-84 (`case "auto": if ctx.Semver.Prerelease != "" { ctx.PreRelease = true }`), `internal/client/github.go` line 544 (the `prerelease` and `make_latest` fields of the release request), and a run of GoReleaser against a mock GitHub API (scratch, not in the repository): tag `v1.0.0-rc1` sent `POST releases` with `draft: true, prerelease: true` and then `PATCH` with `draft: false, prerelease: true, make_latest: "false"`; tag `v1.0.0` sent `prerelease: false`. `goreleaser check` accepts the key. No prerelease tag was published (an immutable tag cannot be reused), so the first real one is the live test. The prerelease refusal in the code stays as a backstop.
- The asset must exist only when an update is due, so a missing asset on an old release is not an error. The asset name contains the OS, so a macOS or Windows build of gdcli fails with `release <tag> has no asset gdcli_macos_aarch64.tar.gz` instead of replacing its executable with a Linux binary.
- `immutable: true` is required. This is hardening, not the basis of the integrity claim (that is the digest): it fails closed if GitHub ever stops reporting the flag or a release was published mutable. If the repository setting is disabled, updates fail with an explicit message and users reinstall as described in the README.
- The `gdcli_checksums.txt` asset is not used: it has the same origin and trust root as the API digest and would cost a second download and a parser; GitHub has computed digests for every asset of this repository.

## Allowed hosts

`github(url)` accepts a URL only if the scheme is `https`, the authority is exactly the host (no userinfo, no non-default port) and the host is `github.com`, `api.github.com` or ends with `.githubusercontent.com`. Every request goes through it: the constant API URL, the `browser_download_url` from the JSON and every redirect target. At most 3 redirects are followed. The real download is `github.com/.../releases/download/...`, one 302 to `release-assets.githubusercontent.com`, then 200. A rejected URL is reported as `scheme://host` only (no userinfo, port, path, query or signed parameters).

The predicate is a separate function and not a shared helper with `google::googleusercontent`: the Google predicate is 6 lines with its own tests; a shared `https_host(url, accepted)` would be about 6 lines, shrink the Google predicate to 3 and the GitHub one to 6, i.e. 15 lines against 6 + 10, one line saved at the price of editing a tested Google path whose port and userinfo behaviour would change or need a parameter.

## Security level

- Integrity, not authenticity. The digest is computed by GitHub and delivered by `api.github.com`; the bytes come from a different host. That stops corruption, truncation and tampering on the download path (CDN, storage, a middlebox that does not also control the API host). Immutable releases prevent changing a published release afterwards.
- Not defended: a compromised GitHub account, token or workflow that publishes a malicious new release with a matching digest, and a compromised root CA in `webpki-roots`.
- `gh attestation verify` is not performed by the program (the build provenance attestation is described in `release.md`; users can verify an asset by hand). Verifying Sigstore bundles from Rust needs `sigstore-verify` (+34 packages including `aws-lc-sys`, a C library); shelling out to `gh` needs a tool most users lack.
- Credentials: `src/update/` imports neither `auth` nor `Google` and never reads the config or data directories; `grep -rnE "crate::auth|Google" src/update` prints nothing. The Google token and client secret are never touched. The only credential the command can send is `GITHUB_TOKEN`, under the rules in the next section.
- Archive handling: the tar entry name is only compared with `gdcli`, never joined to a path; `Entry::unpack` is never called, so names such as `../x`, absolute paths, symlinks and hard links cannot touch the file system, and every other entry is skipped. A `gdcli` entry that is a symlink or a directory is skipped and ends in `archive has no regular file named gdcli`. RUSTSEC-2026-0067 concerns `unpack_in`, which is never called; RUSTSEC-2026-0068 concerns PAX size-header parsing, which `Archive::entries()` uses, so `tar >= 0.4.45` is required.
- Same-user local attackers are out of scope: the staged file is 0600 with a random name, and such an attacker can replace the binary directly.

## GITHUB_TOKEN

- Source: the environment variable `GITHUB_TOKEN` and nothing else. Unset and empty values mean no token; a non-unicode value is sent lossily (invalid sequences become U+FFFD, which a header value accepts) and GitHub rejects it with 401, so it never falls back to anonymous silently (`github_token`, a pure function over the `OsString` that `std::env::var_os` returns, so the cases are unit-tested without touching the process environment). The token is sent exactly as given: a trailing newline or a control character is refused locally, surrounding spaces or quotes go to GitHub (observed on 2026-11-20 with a GitHub App installation token against the genuine `v0.3.0` binary: spaces accepted, quotes answered 401).
- Where it is sent: `Authorization: Bearer <token>` on the request for `releases/latest` only. `bearer()` builds the value with `HeaderValue::from_str` and marks it sensitive (`set_sensitive(true)`: HTTP/2 does not index it in the HPACK table and `Debug` prints `Sensitive`). A redirect hop of that request keeps the header only if its origin (scheme, host and port) equals the origin of the API URL, so a repository-rename redirect inside `api.github.com` stays authenticated; after the first hop that leaves the API origin the header is dropped for the rest of the chain, also for a later hop back to the API origin. `send` reports whether the credential was still attached to the final answer, and the 401 and rate-limit wording depends on that. The host allowlist `github` still decides first about every hop.
- Where it is never sent: the archive download. `Fetcher::archive` calls `send` with no credential, and the token is a parameter of the API call, not state of `Fetcher` or of the client, so even a download URL with the same origin as the API URL (the tests serve both from one server) carries no `Authorization` header. No request to any other host carries it.
- Never visible: the token appears in no error message, no output and no `Debug` text. A value that is not a valid header value (a trailing newline, control characters) stops the command before any request with `GITHUB_TOKEN is not a valid HTTP header value`. The tests assert on every captured message, output and request that the token text is absent or present exactly where specified.
- Failure behaviour: HTTP 401 on an API answer that was requested with the token is `github rejected GITHUB_TOKEN (401): unset it or provide a valid token`; there is no silent retry without the token, so a broken token is visible instead of being masked by the anonymous limit. A 401 on a request that carried no token (none configured, or the chain had left the API origin, or the archive download) is `github api error 401 Unauthorized`. Rate-limit errors name the case (see Bounds). The messages are listed in `commands.md`.
- What the token is for and what it needs: a higher rate limit (5,000 requests per hour per user instead of 60 per IP; https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). A token without scopes is enough for this public repository: GitHub's list of scopes for OAuth apps (https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) states that no scope "grants read-only access to public information (including user profile info, repository info, and gists)". A GitHub App installation token is accepted the same way (exercised on 2026-11-20: HTTP 200 and `x-ratelimit-limit: 5000`). The token that GitHub Actions provides as `GITHUB_TOKEN` is accepted the same way and has its own limit of 1,000 requests per hour per repository (GitHub documentation; not exercised in this repository's runs). Personal access tokens, including fine-grained ones, are described at https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens.
- Threat model: the token goes only to `api.github.com` over https (the allowlist rejects http and other hosts before any request, the origin check drops it on foreign hops, the download call has no parameter for it), it is never logged or printed, and it is not stored or copied anywhere by gdcli. What is not defended: a process that can read the environment of the running `gdcli` already has the token, and a compromised `api.github.com` receives it by definition. `GH_TOKEN`, a flag and files are not supported (see the rejected alternatives): one variable is one place to audit.

## Staging, replacement and ETXTBSY

- Staging happens in the install directory, never in `TMPDIR`: the directory must be writable for the replacement anyway, nothing is staged in tmpfs (RAM), and a non-writable directory fails before the download with `cannot write to <dir>`. Disk use there is about 9 MB during an update (archive 1.8 MB, staged binary 3.7 MB, `self-replace`'s copy 3.7 MB).
- Opening a running executable for writing fails with ETXTBSY; `rename(2)` replaces the directory entry and the running process keeps the old inode. `self-replace` therefore copies the staged file to `.gdcli.__temp__XXXXXX` next to the executable, gives it the permissions of the installed file and renames it over the executable. The update runs from the very file it replaces.
- `current_exe()` is `/proc/self/exe` on Linux, already symlink-resolved: a symlinked `~/.local/bin/gdcli` replaces its target and the link survives.
- Failure atomicity: the only change to the install location is that final rename. The unnamed archive file, the `NamedTempFile` and `self-replace`'s temp file are drop guards, so every error path and the deadline remove them. `SIGKILL`, power loss or Ctrl-C at the wrong moment can leave `.tmpXXXXXX` (ours) or `.gdcli.__temp__XXXXXX` (`self-replace`) in the install directory; both are safe to delete. The installed binary is never partially written.
- `cargo run -- update` would replace `target/debug/gdcli` with the release binary; harmless, cargo rebuilds it.
- A package-manager-owned file (for example in `/usr/bin`) is replaced only if the user can write to its directory; otherwise the command fails early with the path in the message.

## Bounds

- Size: `limit` is 32 MiB (real sizes: 1.8 MB archive, 3.7 MB binary). It bounds the download, the `gdcli` entry (checked with `entry.size()`; `take` would truncate silently) and, times four, the whole inflated stream (`Read::take` on the gzip decoder). Together they bound disk, memory and total inflated bytes against an endpoint that never stops, an oversized entry and a decompression bomb inside a verified archive. An inflated stream cut in the middle of an entry fails with `cannot extract the archive: unexpected EOF`; cut exactly at an entry boundary the tar reader sees a clean end and the error is `archive has no regular file named gdcli`; either way nothing is installed.
- Time: every network wait is bounded by the connect timeout (10 s) and the 120 s deadline of `with_deadline` (`deadline_for` gives every command except `auth setup` and `auth login` that deadline); the deadline drops the future, which drops the staging files. Extraction and replacement are synchronous and the deadline cannot interrupt them; their cost is bounded by the size limits and local disk speed, milliseconds for the real binary.
- Memory: frames go from hyper to the hash and the file; the only buffered body is the API JSON (about 10 KB). Peak RSS of a real update is recorded in `performance.md`.
- Rate limit: 60 requests per hour per IP for unauthenticated API calls, 5,000 per hour per user for a personal access token or OAuth token and at least 5,000 per hour per installation for a GitHub App installation token (GitHub documentation: the minimum is 5,000 requests per hour, the limit scales with the number of users and repositories and cannot increase beyond 12,500 requests per hour, and an installation on a GitHub Enterprise Cloud organization has 15,000 requests per hour; the only authenticated kind exercised here: `x-ratelimit-limit: 5000`), 1,000 per hour per repository for the token that GitHub Actions provides (`x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset`; GitHub documentation, rate limits for the REST API); one run costs one request (the asset download is not a REST call). A 403 or 429 with `x-ratelimit-remaining: 0` becomes the rate-limit error with the reset time; without a token it suggests setting `GITHUB_TOKEN`, with a token it says `github api rate limit of the GITHUB_TOKEN exceeded` (with the reset time when GitHub sends one). Secondary (abuse) limits answer 403 or 429 with `retry-after` and without `x-ratelimit-remaining: 0`; they are reported as `github api error 403 Forbidden` and not handled specially.

## Injection and tests

Production values are written only in `run`: the client from `google::https_builder()` and `google::connector()`, the predicate `github`, the API URL constant, the directory of `current_exe()`, `self_replace::self_replace` and the 32 MiB limit. `run_with(&Fetcher, api, token, &Install, out)` takes everything that differs in tests, the same way `Google::new` and `Paths::resolve` do, so no environment variable, flag or Cargo feature can change where a binary comes from; the only environment variable `run` reads is `GITHUB_TOKEN`, through the pure helper `github_token`, and the tests pass the token as a parameter (`unsafe_code` is forbidden, so they never set a process variable). The 29 tests of `tests/update.rs` run `run_with` in-process against wiremock with a plain-HTTP client, the predicate `github(url) || host == 127.0.0.1`, a fake replace function that copies the staged file to `<dir>/installed`, and small limits. What they cannot cover is the real replacement of a running executable and the production wiring of `run`; that is proven by the real runs against the real release (see `testing.md`), which are a release gate.

Rejected test seams: an environment variable in the release binary (anything that can set the environment of one `gdcli update` decides where the executable comes from), `#[cfg(debug_assertions)]` (ties security code to a profile switch; `cargo test --release` would silently contact GitHub) and a Cargo feature enabled for tests through a self dev-dependency (it works, but it adds a lock self edge and two gates for a seam that plain injection makes unnecessary).

## Verified against the released v0.2.0

- The real self-update script (verification step 8 of `release.md`) printed `E2E-OK` against the genuine `v0.2.0` release: a scratch 0.0.1 build was updated to v0.2.0 (`status: updated`, `current: 0.0.1`, `latest: 0.2.0`); the API digest equals the sha256 of the downloaded asset and the installed file equals the `gdcli` entry of the archive; the mode (775) and owner were preserved and only `gdcli` was left in the directory.
- The updated binary is the genuine release binary, and its own second `update` printed `status: up_to_date`. The equal-version case, a build newer than the release (9.0.0), a symlinked install (the link is kept), mode 700 (kept) and a read-only directory (`error: cannot write to <dir>: Permission denied (os error 13)`, binary unchanged) behave as specified.
- The genuine `v0.2.0` x86_64 binary run in a clean home printed `status: up_to_date`, `current: 0.2.0`, `latest: 0.2.0` and left itself unchanged. Run on 2026-11-19.

## Verified against the released v0.3.0

- The real self-update script (verification step 8 of `release.md`) printed `E2E-OK` against the genuine `v0.3.0` release on 2026-11-20: a scratch 0.0.1 build was updated to v0.3.0 (`status: updated`); the API digest equals the sha256 of the downloaded asset and the installed file equals the `gdcli` entry of the archive; the updated binary's own second `update` printed `status: up_to_date`; the invalid-token case printed exactly `error: github rejected GITHUB_TOKEN (401): unset it or provide a valid token` and left the binary unchanged; the empty-token case was a normal update. The rate limit of repeated runs: see release.md.
- The genuine `v0.3.0` x86_64 binary run in a clean home on 2026-11-20: anonymous, `status: up_to_date`, `current: 0.3.0`, `latest: 0.3.0`; `GITHUB_TOKEN=gdcli-invalid` printed the exact 401 message above; the token of the local `gh` login printed `status: up_to_date`, and a `curl` request with the same token to the same URL returned HTTP 200 with `x-ratelimit-limit: 5000`; an empty `GITHUB_TOKEN` was treated as no token. That token is a GitHub App installation token (prefix class `ghs_`, a `[bot]` account), not a personal access token.

## What stays unverified

Execution of the aarch64 binary and of an aarch64 update (no aarch64 host; the build is checked with `cargo zigbuild --target aarch64-unknown-linux-gnu`, and the released aarch64 binary was only inspected), a root-owned or package-managed install path (covered by the read-only directory run only), and the first real prerelease tag (`v0.2.0` is a normal release; the prerelease handling is proven against the GoReleaser source and a mock API only). The valid-token path (HTTP 200 with `x-ratelimit-limit: 5000`) was exercised manually with a GitHub App installation token and is not part of the e2e block, which cannot hold a secret and therefore covers only the invalid-token (401) and empty-token cases. The token that GitHub Actions provides as `GITHUB_TOKEN` (1,000 requests per hour per repository), fine-grained personal access tokens and classic personal access tokens are documented by GitHub (the pages cited under GITHUB_TOKEN) but not exercised.

## Alternatives rejected

| Alternative | Measured or known cost | Decision |
|---|---|---|
| `self_update` crate | +2,451,448 bytes (+67 %), +39 packages, a second HTTP client (`ureq`), mandatory `regex`, ignores draft, prerelease and immutable, walks all release pages, a fresh agent-assisted 1.x rewrite | rejected |
| `ubi` | +3.45 MB, +86 packages, a `chrono` unmaintained advisory (RUSTSEC-2026-0543) in its tree, in-place copy fails with ETXTBSY | rejected |
| `axoupdater` | needs `dist` install receipts and an installer asset this project does not publish | rejected |
| `binstalk` | +94 packages | rejected |
| Sigstore verification (`sigstore-verify`) | +34 packages including `aws-lc-sys` (C) | rejected, integrity only |
| `sha2` instead of `ring::digest` | `digest`, `block-buffer`, `crypto-common`, `generic-array`, `cpufeatures` and a second SHA-256 | rejected: `ring` is already in the tree |
| manual `(u64, u64, u64)` version compare | about 8 lines plus edge-case tests; accepts `v1.2.3.4` unless written carefully | rejected: `semver` |
| hand-written replace | 12 lines of temp file, copy, chmod and rename | rejected: `self-replace` (48 lines, used by uv, pixi, mise, axoupdater) |
| `miniz_oxide` backend of `flate2` | 3 more packages, slower inflate, 12.5 KB smaller binary | rejected: `zlib-rs` |
| checksum file fallback | same trust root, second download and parser | rejected |
| `--check`, `--json` | extra behaviour, tests and docs | rejected; `--json` exists only where the owner listed it |
| `GH_TOKEN`, a `--token` flag, a config or token file, any other source of a token | each is one more way to send a credential: a flag ends up in shell history and process lists, `GH_TOKEN` belongs to the `gh` tool and may hold a token meant for other uses, a file is state that has to be protected | rejected: `GITHUB_TOKEN` only |
| `CARGO_PKG_REPOSITORY` for the coordinates | needs a `repository` field and runtime parsing | rejected: two constants |
